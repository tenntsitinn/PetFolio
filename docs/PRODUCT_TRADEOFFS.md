# PetFolio 产品取舍讨论总结

> 后续决定（2026-10-20）：产品承诺为“make the Codex Pet useful at a glance”。当前开发版保留毛玻璃和 0–100%、步进 1% 滑块，0–20%（含 20%）自适应文字颜色；Default 禁用毛玻璃及透明度调整。多屏实测通过后再准备 release/development 分支；未来稳定版考虑隐藏毛玻璃并提供三或四档、最低 30% 的不透明度，具体档位未定。下面保留早期讨论记录，未决项应结合此更新阅读。

整理日期：2026-10-19
依据：用户提供的 HANDOFF.md、PETFOLIO_MULTIMONITOR_HANDOFF.md，以及本次项目对话。本文总结讨论与决定，不是功能删除清单，也不代表已完成产品规模或视觉评估。

## 一、这次想解决什么

PetFolio 围绕 Codex Pet 提供附随的信息气泡，目前涉及额度显示、系统使用情况、宠物跟随和外观设置。

产品讨论的重点已从“还能加什么”转向“已有功能哪些值得留下”：作为一个小插件，工程规模是否合理？可选外观带来的体验价值，是否值得它增加的使用负担与维护成本？

这不是单纯追求文件少、代码少或选项少，也不能因为功能已经做完，就默认应该保留。

## 二、用户已经明确的决定

### Default Mode 已定稿

用户原话：“Default Mode我已经确定下来了，现在就是在已经做好的功能上做减法的时候。”

后续讨论以这个默认外观为基线，不重新探索 Default，也不自行增加新的视觉效果。

### 本机插件封装有独立的探索价值

用户原话：“Codex 本机插件封装是我在考虑日后进入plugin market的可能做的尝试。”

因此，插件封装的价值包含分发渠道验证。可以审查它是否保持薄封装、是否重复业务逻辑，但不能只因当前用户少，或认为它只是另一个 EXE 启动入口，就建议删除。

这不等于已经满足未来市场的上架规范，也不构成为未知规范提前建设大量适配的理由。

### 多屏开发保持跟随工具的边界

用户希望推进不同缩放比例下的多屏支持，参考 Codex 原生的坐标和布局思路，不为此引入 Electron。当前仓库实际采用 C# / WinForms / Win32，不因历史摘要中的 C++ 描述而迁移技术栈。

PetFolio 只跟随 Codex Pet，不替宿主修复拖拽故障，不建立独立的持久化位置或自主恢复策略。多屏开发与外观删减是两件事，推进前者不代表后者已作出决定。

## 三、真正纠结的地方

### 毛玻璃的问题最初来自视觉协调性

用户考虑删除毛玻璃，是因为它与 Codex 原生 Bubble 的材质不同，而非已经测出它太慢或太重。

尚未分清的是：毛玻璃本身不好看，还是它与宿主不协调？同时，用户担心如果把“与原生不同”作为删除理由，最终所有个性化选项都会被删掉，只剩 Default。

所以，需要判断具体效果的价值，不能直接把“原生一致”当作已经确定的唯一标准。

### 审美疲劳使继续自问偏好失去作用

用户反复表示自己已经分不清。继续问“你更喜欢哪个”“如果重来还做不做”，无法提供新的判断依据。用户需要的是基于实际效果和工程证据的独立评价。

两位朋友对视觉表现关注不多，其中一位对 1.1.1 已很满意。这是有限的个体反馈，不能推出后续视觉功能没有价值，也不能代表所有用户。

## 四、功能取舍状态

| 项目 | 已明确的状态 | 尚需回答的问题 |
| --- | --- | --- |
| Default Mode | 已定稿 | 不重新设计 |
| Pet Colour Mode | 去留未定 | 相比 Default，是否提供值得保留的个性化体验？ |
| 毛玻璃 | 用户考虑移除，尚未决定 | 实际视觉是否协调？独立渲染路径增加多少维护与运行成本？ |
| 透明度调整 | 连续调节或离散档位未定 | 用户是否需要精细调节？少量档位能否覆盖主要需求？ |
| 低不透明度范围 | 去留未定 | 实际可读性与使用价值如何？是否引入额外补偿逻辑？ |
| 字色自适应 | 去留未定 | 它还服务于哪些场景？与低不透明度是否存在真实、可拆分的依赖？ |
| 本机插件封装 | 有明确的分发探索目的 | 是否保持薄封装？维护成本是否与探索价值相称？ |

关于低不透明度，历史讨论提到 10%–20%；本次读到的项目 README 描述 Pet colour 支持 10%–100%。这只能说明当前文档列出了该功能，不等于已经评估过低档位的视觉表现或必要性。

## 五、提出过、但没有被用户采纳为决定的方案

此前助手提出过以下候选方向：

- 保留 Pet Colour。
- 倾向删除毛玻璃与低不透明度范围。
- 如果依赖关系允许，移除随之不再需要的字色补偿。
- 将透明度改为 3–4 档。
- 形态和交互追求原生感，允许色彩、透明度个性化。

这些是讨论方案，不是用户已经确认的产品原则或实施授权。后续总结、评估和开发都不能把它们写成已拍板事项。

## 六、如何判断“小插件是否已经太大”

需要拆开看四个维度，不能互相替代：

| 维度 | 应检查的证据 | 不能据此直接推断的结论 |
| --- | --- | --- |
| 分发体积 | 独立版、插件版各自的 ZIP、EXE、附带文件大小 | 仓库大不等于安装包大 |
| 运行开销 | 常驻内存、空闲与拖动 CPU、采样查询、外观效果的增量开销 | 代码多不等于运行重 |
| 维护复杂度 | 渲染分支、配置组合、窗口与原生 API、封装重复程度 | 测试和诊断文件多不等于产品臃肿 |
| 使用负担 | 用户看到多少选项、理解和调整它们的成本 | 选项少不自动等于体验好 |

此前助手认为工程投入较充分、视觉功能可能形成了复杂的渲染子系统，但当时没有完成本地代码审计、发布包拆解或性能实测。这是待验证判断，不能据此认定产品过大。

本次多屏开发的构建与自动测试，验证的是开发改动；它们没有完成上述产品规模评估，也没有证明某个外观该删或该留。

## 七、下一次产品评估应交付什么

1. 对照实际界面评价 Default、Pet Colour、毛玻璃和不同不透明度，分别说明视觉效果与宿主协调性，避免只依据模块名称判断。
2. 核实各外观功能的真实依赖：哪些只是参数变化，哪些增加窗口、渲染路径或补偿逻辑。
3. 将视觉收益、运行增量、维护负担与用户选项成本放在一起比较。
4. 给出一到两项优先收敛或删除的候选，明确能减少什么负担、会失去什么体验；证据不足的部分直接列出缺口。
5. 检查插件封装是否保持薄封装，同时保留其分发渠道验证的目的。

需要的是独立、有证据的判断，不是为了已有实现找保留理由，也不是因为“小插件应该简单”就一律删减。当前尚未批准删除任何外观功能。
