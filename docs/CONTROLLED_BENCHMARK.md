# 五组交替性能对照

日期：2026-10-12。Windows build 26200，16 个逻辑处理器。

## 方法

每场景预热 10 秒、测量 30 秒；五组，每组运行对照和优化构建，顺序依次为 AB、BA、AB、BA、AB。源码先复制到隔离目录并冻结，两个 EXE 在全部轮次中保持不变。每个构建使用一个独立进程完成六种场景。共 60 个场景记录，均完成且通过有效性检查。

对照是同一份代码中禁用配置缓存、变化快照过滤和空闲计时器调整的构建，不是历史 Release 二进制；日志、诊断、渲染和服务生命周期保持一致。源码与 EXE 的 SHA256 保存在 [构建清单](performance/controlled/manifest.json)。

使用有效配色缓存、小型隔离配置、假额度来源及独立宠物窗口，实际运行生产 tracker、窗口、合成效果和系统采样。保存位置变化每 100ms 更新一次夹具文件；原生拖动使用系统鼠标输入回放，每约 20ms 移动一次指针，真实拖动钩子必须在测量阶段观察到足够数量的活动拖动更新，否则该场景失败。每次回放后释放鼠标并恢复位置，不修改 Codex 配置或查询账号。

消息循环以 `MsgWaitForMultipleObjectsEx` 等待，避免测量器自身每 5ms 轮询。仍包含夹具写入、输入回放、记录延迟及取消检查的成本。CPU 为一个逻辑核心的占用百分比，不包含 DWM／GPU 和真实 CLI；记录整机背景 CPU 供检查环境波动。内存为阶段结束时工作集。原生输入回放在独立窗口完成，没有测试实际 Codex 客户端的窗口识别或物理鼠标硬件。

延迟从最新的不同输入位置到气泡 HWND 到达对应位置计算，同一输入只计一次，丢弃被后续位置合并的输入。它不是输入到屏幕像素显示的延迟；必须同时看位置更新数量及更新间隔。下面的 P95 是各轮 P95 的中位数，不是汇总所有输入后的 P95。

## 完整长测：重复限流修正之前

CPU 数值为五轮中位数，括号为 Q1～Q3。

| 场景 | 对照 CPU | 优化 CPU | CPU 更低的配对数 |
| --- | --- | --- | --- |
| 静止额度 | 1.15%（1.15～1.30） | 0.31%（0.26～0.36） | 5/5 |
| 保存位置变化 | 3.85%（3.65～4.48） | 3.28%（2.71～3.44） | 4/5 |
| 原生鼠标拖动 | 7.40%（5.10～8.02） | 7.03%（6.14～7.29） | 2/5 |
| 低透明度系统模式 | 1.46%（1.25～1.56） | 0.57%（0.42～0.94） | 5/5 |
| 隐藏气泡 | 0.68%（0.31～0.68） | 0.21%（0.16～0.26） | 4/5 |
| 宠物关闭 | 0.52%（0.42～0.68） | 0.26%（0.21～0.36） | 4/5 |

原生拖动 CPU 波动较大：优化构建在三组中更高，配对 CPU 降幅的中位数为 **-0.89 个单核占用百分点**。因此不能根据两个独立中位数 7.40%→7.03% 宣称原生拖动 CPU 得到了改善。

| 位置更新指标 | 对照 | 优化 |
| --- | --- | --- |
| 保存位置变化：更新次数／秒，中位数 | 8.23 | 8.66 |
| 保存位置变化：P95 最新输入延迟 | 99.38ms | 9.75ms |
| 保存位置变化：P95 更新间隔 | 133.18ms | **209.06ms** |
| 原生拖动：更新次数／秒，中位数 | 30.93 | 31.96 |
| 原生拖动：P95 最新输入延迟 | 19.78ms | 20.03ms |
| 原生拖动：P95 更新间隔 | 63.49ms | 53.93ms |

保存位置变化的延迟受两组 100ms 计时器相位影响：优化后的各轮最新输入延迟 P95 从 9.15ms 到 106.90ms，不能仅挑中位数 9.75ms 宣称响应提升。三轮 P95 更新间隔超过 200ms，说明存在长尾抖动。源码核对发现空闲 100ms 计时器还要满足另一个 100ms 元数据截止时间，稍早或抖动的回调会跳过一次检查。

工作集：静止中位数 53.03→49.47 MiB；原生拖动 55.17→54.81 MiB；系统模式 57.77→57.23 MiB。此结果不构成长时间无泄漏证明。

原始记录和统计：[完整数据目录](performance/controlled/)、[汇总 JSON](performance/controlled/summary.json)。未剔除任何正式样本。准备期间的两秒输入验证和消息循环调整前的取消运行不计入正式统计。

## 修正与针对性复测

修正：空闲 100ms 回调直接检查元数据；只有实际拖动的 16ms 路径使用 100ms 元数据截止时间。配置与 JSON 的缓存校验仍在，只读取已改变的内容。行为测试覆盖元数据截止时间尚未到达时，空闲回调仍观察到新的保存位置。

针对保存位置变化再做五组交替、每轮预热 10 秒和测量 30 秒的复测，全部完成并有效。对照仍使用旧的 16ms 跟随与 100ms 元数据限流；修正构建使用空闲 100ms 回调直接检查缓存元数据。

| 复测指标，五轮中位数 | 对照 | 修正后 |
| --- | --- | --- |
| CPU 单核占用 | 3.33%（Q1～Q3：2.60～3.38） | 3.02%（2.66～3.49） |
| CPU 更低的配对数 | — | **2/5** |
| P95 位置更新间隔 | 131.18ms | **118.81ms** |
| 每轮 P95 更新间隔范围 | 130.70～133.98ms | **118.02～119.66ms** |
| 更新次数／秒 | 8.26 | 9.13 |
| 274 次不同输入的可观测更新数 | 248（245～250） | **274（273～274）** |
| 最新输入延迟中位数 | 48.31ms | 82.71ms |
| P95 最新输入延迟，各轮 P95 的中位数 | 97.20ms | 89.01ms |
| 工作集 | 54.55 MiB | 54.47 MiB |

全部五轮都消除了约 200ms 的 P95 更新间隔，位置更新几乎不再遗漏。最新输入延迟中位数受固定 100ms 计时器相位影响，修正后更高，因此此次结论是**更新连续性改善**，不是所有延迟指标都改善。原生鼠标拖动使用另外的 16ms 路径，其完整长测 P95 最新输入延迟仍约 20ms；不把保存坐标路径的 100ms 等待解释成鼠标拖动延迟。

CPU 配对降幅的中位数为 -0.62 个单核占用百分点，只有两组修正后更低，不能宣称修正后的移动 CPU 有稳定收益。本轮整机背景 CPU 的中位数为对照 5.72%、修正 5.50%，范围仍较宽；所有样本保留，未按结果挑选或剔除。

复测原始记录：[更新连续性复测数据](performance/cadence-fix/)、[汇总 JSON](performance/cadence-fix/summary.json)、[固定构建清单](performance/cadence-fix/manifest.json)。完整六场景 CPU 表来自修正之前的优化版本；修正后的额外复测只针对保存位置变化，不把这两批数值混成同一份基线。

## 复现

```powershell
./benchmark.ps1 -Seconds 30 -Warmup 10 -Rounds 5 -NativeDrag
python ./summarize-benchmark.py .test-build/benchmark-输出的标识
```

原生鼠标回放需要显式 `-NativeDrag`，运行期间会移动鼠标。默认不回放原生输入。聚焦一个场景：

```powershell
./benchmark.ps1 -Seconds 30 -Warmup 10 -Rounds 5 -Scenarios moving-quota
```

脚本在 `.test-build/benchmark-*` 保存固定源码、二进制、哈希、各轮记录。需要停止时，在当前输出目录创建 `cancel` 文件；测量器会在约 250ms 内开始退出并释放、恢复鼠标。汇总工具只接受完整、有效并匹配场景列表的记录。
