# 文件通知更新位置

2026-10-12：`PetStateService` 监听配置和位置文件变化，在界面线程合并通知后更新。合并计时器为 16ms，Windows 消息调度会影响实际等待。原有 100ms 轮询兜底，原生鼠标拖动路径保持原有行为。读取不完整的文件仍会由后续通知或轮询重试；释放后不处理排队回调。

通知回调检查读取计数：若兜底轮询已经读取了该通知对应的变化，不再强制失效缓存。这避免初测中每次位置写入被读取两遍的情况。

## 最终有效对照

固定源码与二进制，参考构建只关闭文件通知，其他实现相同。三组交替顺序，独立窗口每 100ms 写入保存位置，每次预热 3 秒、测量 10 秒。固定测量中的悬停指针位置，验证实际气泡窗口坐标；观测不足 80% 时测量失败。原始记录、源码及二进制哈希见 [记录目录](performance/file-notifications)。这是隔离夹具测量，不代表真实 Codex 客户端所有场景。

| 指标：各轮结果的中位数 | 轮询 | 文件通知 |
| --- | ---: | ---: |
| 最新输入到实际窗口位置的延迟中位数 | 81.34ms | 19.91ms |
| 最新输入延迟 P95 | 89.24ms | 38.87ms |
| 每轮已观测更新 | 91 | 91 |
| 每轮位置文件读取 | 92 | 91 |
| 单逻辑核心 CPU 占用 | 3.90% | 2.65% |

三轮通知路径的延迟中位数范围 19.81–21.08ms，P95 范围 38.79–39.19ms；三轮均观察到全部 91 次输入。CPU 只有两组低于参考，通知构建范围 2.34–4.69%，因此不宣称稳定 CPU 收益。轮询结果仍受写入与轮询计时器相位影响。

初测发现通知与轮询重复解析，已修正。修正后另一次 20 秒测量中有一轮发布了状态但实际窗口位置样本为零，汇总工具拒绝该批次；该批次不用于延迟结论。测量器随后固定悬停指针并增加有效性检查，不能据此断言此前观测失败的唯一原因。较早测量与部分回归测试有重叠，不用于 CPU 收益结论。空闲观察中配置与状态重复解析、快照发布均为零，CPU 仍有波动；没有做足以证明空闲开销等价的长测。
